# People Intelligence 요구사항 대화 원문

## 사용자

당신은 새 People Intelligence 프로젝트를 처음부터 함께 구상하고 실제 제품 완성까지 협업할 제품·UX·데이터·아키텍처 파트너다. 이 대화는 이전 대화의 연속이지만, 기존 세션의 문맥이 없다고 가정하고 아래 내용을 현재 기준으로 사용하라.

# 1. 현재 상황

기존에는 인물·회사·분야 프로필을 제공하는 검색형 People Intelligence 제품을 설계하고 있었다. 그러나 사수의 제안으로 제품 컨셉을 근본적으로 다시 검토하게 되었다.

기존 프로필 중심 설계, 화면 탭, Oracle 선택, API 및 데이터 스키마 논의는 새 제품의 확정 요구사항으로 자동 승계하지 않는다. 필요한 원칙만 다시 검토하고, 새 컨셉과 맞지 않는 결정은 폐기한다.

현재 구상은 다음 문장으로 요약할 수 있다.

> 공개 자료를 LLM이 근거와 시간축을 가진 지식그래프로 축적하고, 사용자가 검색한 노드를 중심으로 관계와 최근 관심도를 탐색하는 동적 지식맵 서비스다.

백엔드의 기준 데이터는 근거 기반 지식그래프이며, 사용자에게 보이는 메인 화면은 그 그래프를 탐색하는 지식맵이다. 두 개념을 혼동하지 않는다.

이 제품은 아직 요구사항 탐색 단계다. 일방적으로 전체 설계를 확정하지 말고, 사용자와 대화하면서 선택지를 설명하고 승인을 받은 뒤 다음 단계로 진행하라.

# 3. 스킬 설치 및 로드 확인

    npx skills add saurabhkumar8112/cyclomatic-complexity-skill@cyclomatic-complexity -g -y

다음 규칙을 지켜라.

- 현재 collaboration mode가 설치를 허용하고 두 스킬이 없다면 위 두 스킬만 설치하라.
- 설치 전 정확한 host와 `CODEX_HOME`을 확인하라.

- 이미 새 세션에서 `grilling` 또는 `grill-me`와 `cyclomatic-complexity`가 노출된다면 설치를 반복하지 말고 요구사항 워크숍을 시작하라.
- `grill-me`의 패키지 이름과 실제 스킬 이름이 다를 수 있다. 설치된 `grilling`이 Matt Pocock의 요구사항 인터뷰 스킬인지 확인하라.
- 다른 스킬, 플러그인, dependency 또는 분석 도구는 설치하지 마라.

## grill-me 적용 방식

`mattpocock/skills@grill-me`는 제품 컨셉과 설계를 결정 트리로 압박 질문하는 용도로 사용한다. 새 컨셉의 요구사항 정의에 즉시 적용하라.

- 사용자에게 질문하기 전에 확인 가능한 사실은 직접 조사하라.
- 질문은 선행 결정이 끝난 것만 제시하라.
- 한 라운드에는 가장 중요한 질문을 최대 3개까지만 묻는다.
- 각 질문에 추천안, 이유, 단점과 대안을 간단히 붙인다.
- 답이 모호하거나 앞선 결정과 충돌하면 그대로 확정하지 말고 다시 확인한다.
- 모든 결정을 `확정`, `제안 중`, `보류`, `제외`로 구분한다.
- 컨셉 범위는 `근거 기반 동적 지식맵 POC`로 제한한다.
- 질문을 무한히 늘리지 말고 다음 구현 결정을 내릴 수 있을 정도로 구체화되면 해당 가지를 종료한다.
- 사용자가 파일 기록을 승인하기 전에는 grill 세션 파일이나 설계 문서를 만들지 않는다.

## cyclomatic-complexity 적용 방식

이 스킬은 지금 요구사항 단계에서 사용하지 않는다.

- 실제 코드가 생긴 뒤 독립적인 세로 구현 단위를 마무리할 때만 사용한다.
- 프로젝트에 선언된 lint 또는 복잡도 기준을 우선한다.
- 복잡도 측정만을 위해 새 dependency를 추가하지 않는다.
- 프로젝트에 분석기가 없으면 수동 측정이나 기존 도구를 사용한다.
- 요구사항이나 데이터 모델을 사이클로매틱 복잡도로 평가하지 않는다.

# 4. 협업 규칙

- 한 번에 거대한 제품 설계나 구현 계획을 내놓지 마라.
- 현재 단계에서 필요한 문제만 다뤄라.
- 한 차례에 질문은 최대 3개까지만 한다.
- 사용자가 답하지 않은 내용을 제품 요구사항으로 확정하지 마라.
- 중요한 선택에는 추천안, 이유, 단점과 대안을 제시하라.
- 사용자의 표현이 기술적으로 모호하면 가능한 의미를 설명하고 선택하게 하라.
- 사용자가 “지식그래프”, “지식맵”, “노드 하나가 정보 하나”라고 표현한 내용을 임의의 표준 정의로 덮어쓰지 마라.
- LLM 또는 Agent가 내부 식별자, 동일 대상 판정, 권한, 허용 관계나 데이터 무결성을 최종 결정하게 하지 마라.
- 모델이 생성한 관계나 해석은 후보로 취급하고 출처·시간·신뢰도·검증 상태를 남겨라.
- 화면상 가까움이나 노드 밀도를 사실로 해석하지 마라. 수집 편향, 노출량, 레이아웃 알고리즘의 영향을 구분하라.
- 관련 인물이 많다는 이유만으로 영업 활동이 활발하다고 단정하지 마라. 관측된 활동과 근거를 통해 설명 가능한 가설로 표현하라.
- 기존 프로필 중심 설계의 결정을 관성적으로 가져오지 마라.
- 데이터베이스와 기술 스택은 새 그래프 요구사항을 정한 뒤 다시 결정하라.
- 단일 화면이라는 목표가 접근성, 상태 표현, 상세 정보와 Evidence Trace를 제거한다는 뜻은 아니다. 필요하면 지도 위의 패널, drawer, overlay를 사용한다.
- 사용자 승인 전에는 프로젝트 파일 변경, dependency 설치, 데이터베이스 생성, migration 실행, 외부 모델 호출을 하지 마라. 위에서 명시적으로 승인된 두 스킬 설치만 예외다.
- LLM Wiki와 구현 사례에 대한 읽기 전용 웹·GitHub 조사는 승인되어 있다.
- 병렬 작업이나 하위 Agent는 사용자가 별도로 승인하지 않으면 시작하지 마라.
- 파일 변경이 승인되어 실제로 이루어질 경우 저장소 `AGENTS.md`의 브랜치·검증·커밋 정책을 따른다.

# 5. 진행 순서

다음 순서를 지켜라.

1. `grill-me`를 사용해 제품 목표, 대상 사용자, 사용자가 얻어야 하는 판단과 POC 성공 기준을 정한다.
2. 지식그래프, 지식맵, 노드, 관계, Claim, 사건, 관측, 출처, 관심도와 관계 강도의 의미를 합의한다.
3. 불변 자료, 후보 지식, 검증된 지식그래프, 화면용 부분 그래프의 경계를 정한다.
4. 단일 지도 홈페이지의 검색, 노드 이동, 확대, 상세 보기, 시간 표현과 실패 상태를 정한다.
5. LLM Wiki의 ingest, query, lint를 제품 흐름에 맞게 구체화한다.
6. 일반 코드와 Agent의 역할을 나누고 모델의 권한, 비용, 실패, 재시도와 검증 방법을 정한다.
7. 데이터 스키마를 먼저 설계한다.
8. 스키마와 사용자 흐름에서 필요한 API만 도출한다.
9. 기능을 독립적으로 검증할 수 있는 세로 단위로 나눈다.
10. 사용자에게 보이는 결과, 최소 happy path, 제외 범위와 검증 방법을 승인받은 뒤 구현한다.

# 6. 현재까지 확정한 제품 방향

다음 내용은 사용자가 이미 승인한 현재 결정이다. 새로운 답변과 충돌하지 않는 한 유지하라.

## 제품 형태

- 제품의 중심은 하나의 지도형 메인 홈페이지다.
- 사용자는 검색으로 원하는 기준 노드를 먼저 찾는다.
- 이후에는 주변 노드를 클릭하고 지도를 이동하면서 관련 정보를 탐색한다.
- 별도 프로필 페이지를 중심으로 구성하지 않는다.
- 상세 정보와 Evidence Trace는 지도 위의 상세 패널 등으로 제공할 수 있다.

## 두 계층 구조

### 1계층: 근거 기반 지식그래프

화면 배치와 무관한 기준 데이터다.

예:

    회사 A ──개발함──> 기술 T
    사람 P ──참여함──> 행사 E ──주최함──> 회사 A
    사람 P ──언급함──> 주제 K

각 관계에는 다음 정보가 연결되어야 한다.

- 출처와 원문 위치
- 관측 시점
- 관계의 유효 기간
- 신뢰도
- 추출 모델과 버전
- 검증 상태

LLM은 후보 노드, 관계와 Claim을 제안한다. 애플리케이션은 허용된 관계 유형, 내부 식별자, 동일 대상 판정, 중복, 출처 연결과 데이터 제약을 검증한다.

### 2계층: 화면용 지식맵

기준 노드, 시간 범위와 표시 규칙에 따라 1계층에서 일부만 골라 만든 화면용 부분 그래프다.

- 전체 데이터베이스를 한 번에 그리지 않는다.
- 검색한 노드의 직접 이웃과 중요한 2단계 이웃만 우선 표시한다.
- 사용자가 다른 노드를 클릭하면 해당 노드를 새로운 중심으로 삼아 주변 그래프를 다시 계산한다.
- 화면용 부분 그래프는 기준 데이터가 아니다. 필요하면 캐시하거나 다시 계산할 수 있다.

## POC 기본 노드

지도에는 다음 노드를 기본 표시한다.

- 사람
- 회사
- 기술
- 주제
- 사건

Claim은 지식그래프에 저장하지만 기본 지도에는 모두 표시하지 않는다. 중요한 Claim만 선택적으로 표시할 수 있으며, 일반 Claim과 출처는 상세 패널에서 확인한다.

## 시각적 의미

- 노드 간 거리는 온톨로지 관계와 연결 강도를 나타낸다.
- 노드 크기와 밝기는 선택 기간의 최근 활동량 또는 관심도를 나타낸다.
- 관계선 굵기는 독립된 근거 수나 검증 강도를 나타낸다.
- 색상은 사람·회사·기술·주제·사건 유형을 나타낸다.
- LLM이 제안했지만 근거가 약한 관계가 필요하다면 점선이나 경고 표현을 사용할 수 있다.
- 관계 강도와 최근 관심도를 하나의 거리 값으로 섞지 않는다.

SNS나 최신 뉴스에서 얻은 키워드 변화는 기존 관계를 덮어쓰지 않는다. 시간별 관측과 관심도 신호로 별도 축적하고 화면 투영에 사용한다.

## 첫 화면

- 실제 전체 그래프를 처음부터 모두 불러오지 않는다.
- 가벼운 대표 지도를 잠시 보여준 뒤 우리 회사 노드로 이동하는 연출을 사용한다.
- 실제 데이터 규모와 무관하게 동작해야 한다.
- 접근성의 `동작 줄이기` 설정에서는 자동 확대·이동 애니메이션을 생략해야 한다.

# 7. DB 컴파일형 LLM Wiki 결정

Karpathy의 LLM Wiki는 특정 구현체가 아니라 패턴이다.

원문: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

우리 제품은 Markdown을 기준 데이터로 사용하는 방식이 아니라 DB 컴파일형을 사용하기로 했다.

| LLM Wiki 개념 | 우리 제품에서의 의미 |
|---|---|
| 불변 raw sources | 정규화 원문과 출처 버전 |
| LLM-maintained wiki | 근거가 연결된 노드·관계·Claim |
| schema | 허용 노드 유형, 관계 유형, 병합·시간·검증 규칙 |
| ingest | 새 자료에서 후보 지식을 추출하고 기존 그래프에 증분 반영 |
| query | 검색한 노드를 중심으로 부분 그래프와 상세 정보를 구성 |
| lint | 출처 없는 Claim, 끊어진 관계, 중복 노드, 모순과 오래된 관계 검사 |

Markdown은 필요할 경우 내보내기 형식으로 사용할 수 있지만 기준 데이터로 두지 않는다.

# 8. Obsidian AI memory 아이디어의 적용 방향

6. 뒤로 가기를 누르면 이전 중심 노드와 상세 내용으로 돌아갑니다.
7. `동작 줄이기` 설정에서는 이동 애니메이션 없이 즉시 HBF로 전환합니다.

작은 팝업보다는 화면 한쪽에 유지되는 상세 패널이나 drawer를 추천합니다. 긴 설명과 출처를 읽기 쉽고, 지도와 정보를 동시에 볼 수 있기 때문입니다. 구체적인 위치와 크기는 화면 UX 단계에서 정하면 됩니다.

단순히 `SK하이닉스 — 관련됨 — HBF`라는 관계선만 저장하면 나중에 다음 정보를 안정적으로 복원하기 어렵습니다.

- 언제 성립하거나 관측된 관계인지
- 어느 문서의 어느 문장이 근거인지
- 여러 출처가 같은 내용을 말하는지
- 서로 충돌하는 Claim이 있는지
- 현재도 유효한 관계인지

지금 합의한 `관계 → Claim → 관측 → 출처` 구조를 사용하면 다시 붙일 필요가 없습니다. 지도에서는 관계를 단순하게 보여주고, 상세 패널에서 시간과 Evidence Trace를 펼치면 됩니다.

## 추천하는 적용 방식

`3d-force-graph`의 3D 좌표·렌더링·노드 포커스 기능을 기술 후보로 두고, Armillary에서 확인한 깊이 표현을 적용하는 방식이 가장 잘 맞습니다.

- 가까운 노드는 더 크고 선명하게 보입니다.
- 먼 노드는 작고 흐리게 보입니다.
- 선택한 노드는 빛과 테두리로 강조합니다.
- 관계선은 뒤쪽으로 갈수록 자연스럽게 흐려집니다.
- 어두운 배경과 제한된 bloom으로 별처럼 보이게 합니다.
- HBF를 선택하면 카메라가 HBF를 바라보는 위치로 부드럽게 이동합니다.
- 상세 패널은 3D 장면과 분리된 일반 HTML 영역으로 두어 가독성과 키보드 접근성을 확보합니다.

다만 노드 라벨을 모두 3D 공간에 띄우면 겹침과 프레임 저하가 발생할 수 있습니다. 실제 `3d-force-graph` 사용자 사례에서도 라벨 위치와 렌더링 성능 문제가 보고되어 있습니다. 따라서 중심 노드와 중요한 이웃에만 라벨을 표시하고 나머지는 hover·focus 때 보여주는 것이 적합합니다. [라벨 표시 제약](https://github.com/vasturiano/3d-force-graph/issues/669), [큰 그래프의 렌더링 논의](https://github.com/vasturiano/three-forcegraph/discussions/44)

### 1. 불변 자료에는 어디까지 저장할까요?

**이유:** 나중에 원문이 수정되거나 사라져도 어떤 문장을 근거로 사용했는지 확인할 수 있습니다.

### 2. 후보 지식이 언제 검증된 지식그래프에 들어갈까요?

**추천안:** 다음 세 상태를 구분합니다.

- `후보`: LLM이 제안한 노드·관계·Claim으로, 아직 지도에 표시하지 않습니다.
- `근거 확인됨`: 애플리케이션이 허용 유형, 내부 식별자, 출처 위치, 시간 형식, 중복과 데이터 제약을 확인했습니다.
- `사람 확인됨`: 사람이 원문과 해석을 직접 검토한 선택적 상위 상태입니다.

애플리케이션 검사를 통과했다는 것은 “객관적으로 참”이라는 뜻이 아닙니다. 해당 Claim이 실제 출처에 연결되고 구조적 규칙을 통과했다는 뜻입니다. 같은 대상인지 모호하거나 출처끼리 충돌하면 자동 병합하지 않고 `검토 필요`로 보냅니다.

**이유:** 모든 Claim을 사람이 확인하지 않아도 POC를 운영할 수 있으며, 자동 검증과 사람의 판단을 혼동하지 않습니다.

**단점:** `근거 확인됨` 상태에도 출처 자체의 오류나 편향이 남을 수 있습니다.

**대안:** 사람이 승인한 지식만 게시하면 신뢰도는 높지만 ingest 속도가 매우 느려집니다. 반대로 LLM 후보를 바로 게시하면 빠르지만 잘못된 관계가 기준 데이터에 섞일 수 있습니다.

이 상태 구분과 자동 승격 범위를 채택할까요?

## LLM Wiki와 검색의 관계

Karpathy의 LLM Wiki는 검색 알고리즘이 아니라 `축적된 지식을 먼저 검색한 뒤 답을 구성한다`는 운영 패턴입니다. 원문에서도 작은 규모에서는 `index.md`를 사용하고, 커지면 선택적으로 BM25·벡터 검색을 제공하는 별도 도구를 붙이는 방식을 설명합니다. 따라서 우리 제품에서는 LLM Wiki의 `query` 흐름 안에 키워드·벡터 검색을 구현한다고 보는 것이 정확합니다. [Karpathy의 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

PostgreSQL은 `tsvector`, GIN 인덱스, `ts_rank`와 `ts_rank_cd`를 이용한 전문 검색과 순위 계산을 기본 제공합니다. PostgreSQL 자체의 미리 정의된 순위 함수는 BM25가 아니므로, BM25를 반드시 사용하려면 별도 구현이나 확장이 필요합니다. POC에서는 우선 PostgreSQL 기본 전문 검색을 평가하고, 결과가 부족할 때만 BM25 도입을 검토하는 편이 작습니다. [PostgreSQL 전문 검색과 순위 계산](https://www.postgresql.org/docs/current/textsearch-controls.html)

벡터 검색은 PostgreSQL에 pgvector를 붙이는 방식이 자연스러운 후보입니다. pgvector 공식 문서도 PostgreSQL 전문 검색과 벡터 결과를 함께 구하고 Reciprocal Rank Fusion 등으로 결합하는 방식을 안내합니다. 다만 pgvector 설치와 임베딩 모델 선택은 아직 승인된 구현 작업이 아니므로 지금 설치하지는 않습니다. [pgvector의 Hybrid Search](https://github.com/pgvector/pgvector#hybrid-search)

## 시간 표현 수정안

선 굵기는 이미 `근거 강도`로 확정했으므로 시간 감쇠에는 사용하지 않는 것을 추천합니다.

| 시각 속성 | 의미 |
|---|---|
| 노드 크기·밝기 | 관측 활동량과 최근성 |
| 관계선 굵기 | 근거 강도 |
| 노드·관계선 투명도 | 오래된 정도 |
| 등장 애니메이션 | 전체 기록에서 과거 정보가 추가되는 과정 |

`전체 기록 보기`를 누르면 현재 90일 지도는 유지하면서 과거 노드와 관계를 비교적 최근인 것부터 오래된 순서로 추가합니다. 오래된 정보일수록 투명하게 표시하되 완전히 보이지 않게 만들지는 않습니다. `동작 줄이기`에서는 애니메이션 없이 최종 상태를 즉시 표시합니다.

임의의 기간 구간마다 상수를 곱하기보다 연속적인 시간 감쇠를 추천합니다. 예를 들어 시간이 두 배 지날 때마다 시각적 강조가 일정 비율로 줄어드는 반감기 방식을 사용할 수 있습니다. 정확한 반감기와 최소 투명도는 HBF 데이터의 실제 분포를 본 뒤 정하고, 지금은 보류합니다.

### 2. 키워드와 벡터 결과를 어떻게 합칠까요?

```text
        ↓
```

벡터 검색은 검색 결과를 찾는 데만 사용하며, 동일 대상 병합이나 관계 생성에는 사용하지 않습니다.

### 2. 한 자료의 반영은 원자적으로 처리할까요?


## GDELT 스냅샷 라운드

## 다섯 번째 라운드 마무리: lint

### 1. lint를 차단 검사와 경고 검사로 나눌까요?

**추천안:** 후보를 검증된 지식그래프에 반영하기 전에 다음 검사를 실행합니다.

`반영 차단`:

- 출처나 원문 위치가 없는 Claim
- 허용되지 않은 노드·관계 유형
- 식별되지 않은 관계의 시작·끝 노드
- 잘못된 날짜와 유효 기간
- 내부 식별자 충돌
- 추출 모델·프롬프트 계보 누락

차단된 후보는 `보류` 또는 `거절됨`으로 이동합니다. 나머지 유효 후보는 하나의 트랜잭션으로 반영합니다.

`경고만 기록`:

- 출처끼리 충돌하는 Claim
- 독립 출처가 하나뿐인 관계
- 다른 노드와 연결되지 않은 고립 노드
- 비슷하지만 병합 여부가 불명확한 노드

**이유:** 데이터 무결성 오류는 막으면서, 출처 충돌처럼 조사할 가치가 있는 정보는 지워버리지 않습니다.

**단점:** 경고가 쌓이면 별도의 검토 우선순위가 필요합니다.

**대안:** 모든 lint 경고를 차단할 수 있지만, 유효한 정보까지 반영되지 않을 가능성이 큽니다.

이 구분을 채택할까요?

### 2. 서로 충돌하는 Claim을 지도에 표시할까요?

**추천안:** 양쪽 Claim이 모두 `근거 확인됨`이라면 관계를 삭제하지 않고 점선으로 표시합니다. 상세 패널에는 서로 다른 주장과 각각의 출처를 나란히 보여줍니다.

- LLM은 어느 쪽이 참인지 최종 결정하지 않습니다.
- 사람이 한쪽을 거절하면 거절된 Claim은 지도에서 사라집니다.
- 동일 대상 여부 자체가 불명확하면 관계를 `보류`하고 지도에서 숨깁니다.

**이유:** 출처 간 충돌은 오류일 수도 있지만, 사용자가 알아야 할 실제 논쟁이나 정보 변화일 수도 있습니다.

**단점:** 점선이 많으면 지도가 복잡해질 수 있습니다.

**대안:** 사람이 검토할 때까지 충돌 관계를 모두 숨길 수 있지만, 중요한 불확실성도 보이지 않게 됩니다.

`근거가 있는 충돌은 점선 + 상세 경고`로 확정할까요?

### 3. 90일 스냅샷과 전체 기록 보기의 충돌을 어떻게 처리할까요?

현재 결정대로라면 DB에 90일 자료만 있으므로 `전체 기록 보기`를 눌러도 90일보다 오래된 노드가 나타나지 않습니다.

**단점:** 과거 노드가 순차적으로 나타나는 연출은 이번 POC에서 확인할 수 없습니다.

POC에서는 전체 기록 보기 검증을 제외할까요, 아니면 스냅샷 범위를 1년으로 넓힐까요?

## ingest의 의미

이 제품에서 ingest는 단순히 문서를 DB에 넣는 작업이 아닙니다. 공개 자료를 읽어 지도에서 사용할 수 있는 근거 기반 지식그래프로 컴파일하는 전체 과정입니다.

```text
GDELT 발견 결과
→ 원문 수집·정규화
→ Agent의 후보 지식 추출
→ 코드의 식별·검증·중복 처리
→ lint
→ 검증된 지식그래프 반영
→ 검색·지도·설명용 데이터 갱신
```

사용자가 검색하거나 노드를 클릭할 때 실행되는 과정이 아니라, 자료가 새로 들어왔을 때 백그라운드에서 미리 수행되는 과정입니다.

HBF 자료 하나를 예로 들면 다음과 같습니다.

### 1. 자료 발견과 원문 보존

GDELT에서 HBF 관련 기사를 발견한 뒤, 실제 기사 원문을 HTTPS로 가져옵니다. 정규화 본문과 제목, 작성자, 게시일, 원문 URL, 수집 시점, 원문 해시를 출처 버전으로 저장합니다.

GDELT 메타데이터만 있고 원문을 확보하지 못했다면 기사 발견 기록으로는 남길 수 있지만, Claim을 `근거 확인됨`으로 올리는 근거로는 사용하지 않습니다.

### 2. Agent의 후보 추출

Agent는 원문에서 다음과 같은 후보를 구조화해 제안합니다.

- 노드 후보: `SK하이닉스`, `SanDisk`, `HBF`, 관련 행사
- 사건 후보: HBF 공개, 공동 발표, 표준 제안 등의 특정 사건
- 관계 후보: 회사가 기술을 개발하거나 발표에 참여했다는 연결
- Claim 후보: 원문이 주장하는 구체적인 문장
- 관측 후보: Claim을 뒷받침하는 정확한 원문 위치
- 시간 정보: 발표일, 사건일, 관계의 유효 기간
- 추출 계보: 사용한 모델·버전·프롬프트 버전

이 결과는 곧바로 기준 지식그래프에 들어가지 않고 staging 영역의 후보로만 저장됩니다.

### 3. 동일 대상 판정과 검증

일반 코드와 DB가 기존 그래프를 조회하여 명확한 동일 대상을 연결합니다. 예를 들어 `SK hynix`, `SK하이닉스`, 이미 등록된 공식 식별자가 명확히 일치하면 같은 노드로 연결할 수 있습니다.

이름만 비슷하거나 같은 이름의 사람이 여럿 있는 경우에는 Agent의 추측으로 병합하지 않고 `보류`로 보냅니다. 허용되지 않은 관계 유형, 존재하지 않는 원문 위치, 잘못된 날짜, 끊어진 노드 연결도 이 단계에서 차단합니다.

같은 사건이나 주제라면 동일 노드를 재사용하되, 각 문서에서 발견된 Claim·관측·출처는 별도로 누적합니다. 따라서 지도 노드 수가 불필요하게 늘어나지 않으면서도 여러 근거와 관점을 잃지 않습니다.

### 4. lint

차단 검사는 기준 그래프에 들어갈 수 없는 오류를 잡습니다.

- 출처 또는 원문 위치가 없음
- 허용되지 않은 노드·관계 유형
- 관계의 시작점이나 도착점이 없음
- 날짜나 유효 기간이 성립하지 않음
- 추출 모델과 출처 계보가 없음

경고 검사는 저장은 가능하지만 검토할 가치가 있는 상태를 표시합니다.

- 출처끼리 Claim이 충돌함
- 출처 다양성이 낮음
- 모호한 동일 대상 후보가 있음
- 다른 지식과 연결되지 않은 노드가 생김

충돌 자체는 제거하지 않습니다. 양쪽 Claim을 유지하고 지도에는 점선으로 표현하며, 상세 패널에서 공통 사실과 각 출처의 관점을 정리합니다.

### 5. 원자적 반영

차단 검사를 통과한 노드·관계·Claim·관측·출처 묶음만 짧은 DB 트랜잭션으로 함께 반영합니다. 중간에 하나라도 실패하면 전체를 롤백하므로, 절반만 연결된 사건이나 출처 없는 관계가 기준 그래프에 남지 않습니다.

중요한 점은 원문 수집이나 모델 호출을 DB 트랜잭션 안에서 기다리지 않는 것입니다. 외부 호출은 staging에서 먼저 끝내고, 준비된 결과를 기준 그래프로 승격하는 짧은 구간만 트랜잭션으로 묶어야 장애가 DB 잠금으로 번지지 않습니다.

### 6. 검색·지도용 파생 데이터 갱신

그래프 반영이 끝나면 영향을 받은 노드에 대해서만 다음 자료를 갱신합니다.

- PostgreSQL 전문 검색용 `tsvector`
- 벡터 검색용 임베딩
- 90일 관측 활동량
- 근거 수와 검증 상태를 바탕으로 한 관계선 굵기
- 1년 전체 기록 보기의 시간별 투명도
- 맥락 설명 1개
- 후속 질문 2개

맥락 설명과 후속 질문 생성에 실패해도 검증된 그래프 자체를 되돌릴 필요는 없습니다. 해당 설명을 `갱신 중` 또는 `생성 실패`로 두고 재시도하며, 이전 설명을 최신인 것처럼 보여주지는 않는 방식이 안전합니다.

현재 상태는 역할 분담과 재시도 정책은 `확정`, 위 두 ingest 경계는 `제안 중`입니다. 파일이나 코드는 변경하지 않았습니다.

## 2. 관계를 여러 Claim의 집계로 표현

추천안은 관계 하나를 출처마다 중복 생성하지 않고, 여러 Claim이 같은 관계를 지지하거나 반박할 수 있게 하는 것입니다.

```text
SK하이닉스 ──개발함──> HBF

        Claim A: 관계를 지지함

```

각 Claim에는 하나 이상의 관측이 연결되고, 각 관측은 출처 버전과 정확한 원문 위치를 가리킵니다. Claim 하나가 여러 관계나 노드 속성을 설명할 수도 있으므로 Claim과 관계는 다대다 연결을 허용합니다.

이 구조를 사용하면 다음 계산이 가능합니다.

- 서로 독립된 지지 출처가 많으면 관계선을 굵게 표시합니다.
- 지지 Claim과 반박 Claim이 함께 있으면 관계선을 점선으로 표시합니다.
- 상세 패널에서 지지 근거와 반박 근거를 나누어 보여줍니다.
- 기사마다 같은 관계선이 중복 생성되는 것을 방지합니다.

단점은 관계, Claim, 관측 사이의 연결 구조가 단순한 엣지 테이블보다 복잡하다는 점입니다. 대안은 기사마다 관계를 하나씩 만드는 방식이지만 중복 관계와 충돌 처리가 어려워집니다. 이 방식으로 확정할까요?

## 3. 허용 관계 유형의 버전 관리

추천안은 관계 유형을 자유 문자열이나 고정된 DB enum으로 저장하지 않고, 사람이 관리하는 버전 있는 관계 유형 목록으로 관리하는 것입니다.

각 관계 유형에는 다음 규칙이 포함됩니다.

- 관계 코드와 표시 이름
- 허용하는 시작 노드 유형
- 허용하는 도착 노드 유형
- 방향이 있는지 여부
- 반대 방향 관계 유형
- 대칭 관계인지 여부
- 사건 노드를 거쳐야 하는지 여부
- 유효 기간이 필요한지 여부
- 활성·폐기 상태
- 온톨로지 버전

예를 들면 다음과 같습니다.

```text
참여함: 사람·회사 → 사건
발표함: 사건 → 기술
개발함: 회사 → 기술
언급함: 사람·회사·사건 → 기술·주제
```

## 1. 노드마다 검색용 문서를 하나씩 생성

추천안은 공개 지도 버전마다 노드별 검색 문서를 만들고, 키워드 검색과 벡터 검색이 같은 문서를 사용하게 하는 것입니다.

검색 문서에는 다음 내용을 포함합니다.

- 대표 이름과 별칭
- 노드 유형
- 근거 확인된 주요 Claim
- 연결된 사건과 주변 노드의 이름
- 미리 생성된 맥락 설명
- 검색 이유를 설명할 Claim과 관계 식별자

원문 기사 전체는 검색 문서에 넣지 않습니다. 기사에 우연히 등장한 단어가 노드 검색 순위를 과도하게 높일 수 있기 때문입니다. Claim과 출처는 검색 문서 작성과 순위 계산에 사용하지만 검색 결과는 기존 결정대로 노드만 반환합니다.

같은 검색 문서에서 PostgreSQL 전문 검색용 데이터와 pgvector 임베딩을 생성합니다. 키워드 검색은 이름과 별칭에 높은 가중치를 주고, Claim과 맥락 설명에는 낮은 가중치를 줍니다.

단점은 Claim이 변경되면 영향을 받은 노드의 검색 문서와 임베딩을 다시 만들어야 한다는 점입니다. 대안은 Claim과 출처를 각각 검색한 뒤 실행 시점에 노드로 합치는 방식이지만 검색 결과 설명과 중복 제거가 복잡해집니다. 노드별 검색 문서 방식으로 확정할까요?

## 2. 파생 데이터를 덮어쓰지 않고 버전별로 저장

추천안은 임베딩, 맥락 설명, 후속 질문, 검색 문서를 생성할 때 기존 결과를 덮어쓰지 않는 것입니다.

각 파생 결과에는 다음 정보를 연결합니다.


새 그래프 버전의 파생 결과가 모두 준비되면 해당 결과들을 새 지도 버전에 연결합니다. 실패한 결과는 이전 완성본과 섞지 않습니다. 동일한 입력·모델·프롬프트 조합의 성공 결과가 있다면 재사용합니다.

이 방식은 특정 지도 버전에서 어떤 설명과 임베딩을 사용했는지 추적할 수 있습니다. 단점은 이전 파생 결과가 계속 쌓이므로 보존 기간이나 정리 정책이 나중에 필요하다는 점입니다. 대안은 현재 결과만 덮어쓰는 방식이지만 실패 시 이전 완성본을 복원하거나 결과 계보를 확인하기 어렵습니다. 버전별 저장 방식으로 확정할까요?

## 3. 충돌하는 Claim을 별도 묶음으로 관리

추천안은 충돌 관계를 단순 경고 문자열로 저장하지 않고 `충돌 Claim 묶음`으로 관리하는 것입니다.

충돌 묶음에는 다음 내용이 들어갑니다.

- 비교 대상인 관계 또는 속성
- 지지하는 Claim 목록
- 반박하거나 다른 내용을 주장하는 Claim 목록
- 비교 대상 기간
- 충돌 후보를 제안한 Agent와 모델·프롬프트 버전
- 공통으로 확인되는 내용
- 관점 정리
- 후보·확인·기각 상태
- 사람의 처리 이유와 시점

Agent는 충돌 후보와 관점 정리를 제안할 수 있지만 충돌 여부를 최종 확정하지 않습니다. 두 Claim이 모두 `근거 확인됨`이고, 대상·속성·기간·표현 성격을 비교할 수 있을 때 사람이 충돌 묶음을 확인합니다. 시점이나 표현 성격이 다른 경우에는 충돌로 확정하지 않습니다. 예를 들어 `2027년 상용화가 목표다`와 `2027년에 상용화되었다`는 서로 다른 표현 성격이므로 자동으로 같은 주장으로 취급하지 않습니다.

확인된 충돌 묶음이 있는 관계만 지도에서 점선으로 표시합니다. 상세 패널에는 승패 판정 대신 공통 사실, 각 Claim의 근거, Agent가 생성한 관점 정리를 보여줍니다.

  가장 중요한 의존성은 출처 버전 → 관측 → Claim → 관계입니다. 관계선이 출처를 직접 들고 끝나는 구조로 만들지 않습니다. 하나의 원문 범위가 여러 Claim을 뒷받침할 수 있고, 하
  나의 Claim이 여러 관측과 관계를 연결할 수 있어야 하기 때문입니다. 반대로 지도용 노드 크기·점선·투명도는 이 체인에서 계산되는 파생 결과이며 기준 지식으로 되돌아가지 않습
  니다.

  각 영역에서 특히 신경 쓸 점은 다음과 같습니다.

  - 온톨로지는 자유 문자열을 막고 과거 의미를 보존해야 합니다. 관계 유형과 속성 정의는 버전, 허용 시작·도착 유형, 방향성, 값 유형을 포함합니다.
  - 출처 버전은 덮어쓰지 않습니다. 정규화 규칙도 버전으로 남기고, Evidence Trace의 문자 위치가 한국어·영어에서 다르게 해석되지 않도록 오프셋 단위를 하나로 고정해야 합니다.
  - 노드 이름은 식별자가 아닙니다. 병합 후에도 이전 식별자와 모든 근거를 유지하고, 모호한 병합은 자동 확정하지 않습니다.
  - Claim은 읽을 수 있는 문장과 기계가 검사할 수 있는 구조를 함께 가집니다. 사실·계획·예측·의견, 값 유형, 시간 범위를 분리해야 합니다.
  - 관계는 출처별로 복제하지 않습니다. 시작 노드·관계 유형 버전·도착 노드·관련 사건·유효 기간이 같은 관계에 지지·반박 Claim을 모읍니다.
  - 상태는 현재값만 덮어쓰지 않고 전이 이력을 남깁니다. Agent는 후보만 만들며, 코드 검증과 사람의 처리가 어떤 상태를 만들었는지 구분합니다.
  - 충돌은 Agent 제안 단계부터 호박색 점선으로 공개할 수 있지만, 두 근거가 비교 가능한지는 일반 코드가 먼저 검사합니다. 충돌 거절과 Claim 거절은 별도 상태입니다.
  - ingest의 외부 호출은 DB 트랜잭션 밖에서 끝냅니다. 준비된 승격 묶음만 짧게 원자 반영하고, 실패하면 기존 그래프를 유지합니다.
  - 파생 결과는 입력 해시·그래프 버전·모델·프롬프트·출력 스키마 버전에 묶습니다. 이전 결과를 덮어쓰지 않고 완성된 HBF 스냅샷만 공개합니다.
  - 검색은 노드 문서를 반환하지만 검색 이유가 된 Claim·관계 식별자를 함께 보존해야 합니다. 그래야 결과 설명이 가능합니다.
  - PostgreSQL 제약으로 LLM의 권한을 제한해야 합니다. 허용 유형, 필수 근거, 정확한 원문 범위, 고유 관계, 대칭 관계 정규화, 상태 전이는 애플리케이션 검증만 믿지 않고 DB에서
    도 막아야 합니다.

  설계 산출물은 ER 구조만으로 부족합니다. 논리 엔터티 목록 + 각 필드의 의미 + 키와 카디널리티 + 불변조건 + 상태 전이 + ingest/승격/공개 흐름 + HBF 예시 데이터 + lint 검사
  표까지 있어야 구현자가 임의로 해석하지 않습니다. 실제 PostgreSQL 테이블명, 타입, 인덱스와 DDL은 이 논리 모델 승인 뒤에 정하는 것이 안전합니다.

  이제 논리 모델에 영향을 주는 세 가지 선택만 확인하겠습니다.

  웹페이지 HTML을 일시적으로 수신
  → 본문을 정규화된 텍스트로 변환
  → 정규화된 텍스트와 메타데이터만 출처 버전으로 저장
  → HTML은 저장하지 않음
  → Agent가 정규화된 텍스트에서 지식 후보 추출
  → 후보 계층에서 lint·동일 대상·중복 검사

  후보 Claim

  후보 계층이 필요한 이유는 다음과 같습니다.

  - Agent 결과가 검증되기 전에 기준 그래프를 오염시키지 않습니다.
  - 일부 후보가 실패해도 기존 그래프를 그대로 유지합니다.
  - 모호한 동일 대상 후보를 보류할 수 있습니다.
  - 거절된 후보와 이유를 보존해 같은 제안의 반복을 막습니다.
  - 어떤 Agent 출력이 어떤 기준으로 승격되거나 거절됐는지 추적할 수 있습니다.

  따라서 staging이라는 표현이 원문 임시 저장소처럼 들리지 않도록 앞으로는 지식 후보 계층이라고 부르겠습니다. 또한 LLM Wiki의 raw source도 이 제품에서는 HTML 원본이 아니라

    "claims": [],
    "observations": [],
    "identity_candidates": []

  별자·토큰 사용량·오류는 Agent 실행 메타데이터로 따로 남깁니다.

  JSON만 저장하면 “노드 후보 하나는 보류, 관계 후보 하나는 거절, Claim 두 개는 승격”처럼 항목별 상태를 관리하기 어렵습니다. 반대로 후보 노드·관계·Claim마다 기준 그래프와
  같은 테이블을 다시 만들면 스키마가 거의 두 벌이 됩니다. 그래서 JSON 전체는 재현과 감사를 위해 보존하고, 각 후보는 다음 정도만 공통 행으로 꺼냅니다.

  후보 식별자
  Agent 실행 식별자
  후보 종류
  JSON 안의 위치
  후보 fingerprint
  현재 상태
  lint 결과
  보류·거절 이유
  승격된 기준 데이터 식별자

  후보의 구체적인 필드는 JSON에 있고, 검증을 통과해 승격될 때만 엄격한 노드·관계·Claim 테이블로 변환합니다. 후보 계층은 의도적으로 신뢰하지 않는 입력 영역이고, 기준 지식그
  래프만 강한 관계형 제약을 적용하는 구조입니다.

  이제 이 방식을 포함해 중단된 세 결정을 다시 확인하겠습니다.

• 맞습니다. 사용자가 말한 **“새 지식을 관계에 반영하고 지도에 보이게 한다”**가 바로 제가 말한 공개 과정입니다. 별도의 제품 기능을 하나 더 만들자는 뜻은 아닙니다. 제가
  graph revision 공개라는 내부 용어로 설명해서 복잡해졌습니다.

  새 기사에서 SK하이닉스 ──개발함──> HBF라는 관계가 발견됐다고 가정하면 내부에서는 다음 순서가 필요합니다.

  1. 기준 지식그래프에 노드·관계·Claim·관측을 원자적으로 승격
  2. SK하이닉스와 HBF의 검색 문서·임베딩·맥락 설명·후속 질문 갱신
  3. 새 관계와 갱신된 파생 데이터가 함께 준비됐다고 표시
  4. 사용자가 다음에 검색하거나 노드를 클릭하면 새 관계를 포함해 지도 재계산

  1번 직후에는 기준 그래프에 새 지식이 존재하지만, 2번이 실패했다면 상세 설명이나 검색 정보는 아직 이전 상태일 수 있습니다. 앞서 사용자가 “노드가 먼저 보이고 관계가 나중에
  붙으면 혼란스럽다”고 했기 때문에, 영향받은 지식 묶음과 파생 결과가 모두 준비된 뒤 지도 조회에 함께 포함하자는 의미였습니다.

  전체 HBF 지도를 하나의 거대한 버전으로 묶을 필요는 없습니다. 더 단순하게 다음처럼 바꾸겠습니다.

  promotion_batch
  ├─ 이번에 승격한 노드·관계·Claim
  ├─ 영향을 받아 갱신한 검색·설명·질문
  └─ publication_state: preparing | ready | failed

  - preparing: 기준 그래프에는 있지만 지도·일반 검색에서는 아직 사용하지 않습니다.
  - ready: 다음 검색·클릭부터 새 지식과 파생 결과를 함께 사용합니다.
  - failed: 기준 그래프는 보존하고 재시도하며, 기존 공개 결과를 유지합니다.
  - rejected: 사람에게 거절된 지식은 즉시 제외합니다.

  이 구조에는 전역 지도 버전이나 지도 구성원 저장이 필요하지 않습니다. 공개 준비가 끝난 변경 묶음만 동적 지도 조회에 누적됩니다. 사용자가 보고 있는 현재 지도는 그대로 유지
  하고, 방금 선택한 것처럼 다음 탐색부터 변경을 반영합니다. 이제 이 의미로 한 가지만 확인하겠습니다.

  # People Intelligence 논리 데이터 스키마 설계 계획

  ## 1. 설계 원칙

  - 전체 모델을 불변 정규화 원문 → 지식 후보 → 기준 지식그래프 → 파생 데이터 → 동적 지도 조회로 구성한다.
  - HTML은 정규화 과정에서만 일시적으로 사용하고 저장하지 않는다.
  - Agent 출력은 후보이며, 식별자·병합·허용 유형·승격·무결성은 일반 코드와 DB가 결정한다.
  - 기준 지식의 의미는 덮어쓰지 않는다. 수정 시 새 기록을 만들고 기존 기록의 상태 이력을 남긴다.
  - 지도 배치와 주변 노드 구성은 기준 지식이 아니다. 지도 조회 시 부분 그래프를 계산하고 브라우저가 3D 좌표를 정한다.

  ## 2. 논리 모델

  ### 출처와 원문

  - discovery_snapshot: GDELT 쿼리, 기간, API 응답, 응답 해시, 통신 방식
  - discovery_hit: 발견된 기사 URL과 GDELT 메타데이터
  - source: 정규화된 URL, 작성자·매체 메타데이터, 원문 언어
  - source_version: 정규화 본문, 본문 해시, 게시·수정·수집 시점, 정규화 규칙 버전
  - evidence_group: 복제·재게시·번역 자료를 하나의 독립 근거로 묶는 단위
  - 작성자와 매체는 기본적으로 메타데이터이며, 일반 노드 기준을 별도로 충족할 때만 후보로 만든다.

  ### Agent 실행과 지식 후보

  - model_task: 작업 종류와 입력 해시를 기준으로 재시도와 결과 재사용을 묶는다.
  - agent_attempt: 모델·프롬프트·출력 스키마 버전, 시도 순서, 응답 식별자, 사용량, 오류
  - structured_output: 계약을 통과한 JSONB 전체를 보존한다. 모델 제공자의 HTTP 응답 전체는 저장하지 않는다.
  - candidate_item: 후보 종류, JSON 위치, fingerprint, 상태, lint 결과, 보류·거절 이유, 승격 대상 식별자
  - 후보 상태는 제안됨 → 검사 중 → 차단됨/보류/거절/승격으로 관리한다.
  - 동일 후보와 동일 출처 버전의 거절 fingerprint는 반복 생성을 억제한다. 새로운 출처 근거가 있으면 새 후보를 허용한다.

  ### 온톨로지와 노드 정체성

  - ontology_version: 노드·관계·속성 규칙의 묶음 버전
  - node_type_definition: 사람·회사·기술·주제·사건
  - relation_type_revision: 방향성, 대칭성, 반대 관계, 허용 시작·도착 유형, 사건 필요 여부
  - attribute_definition: 속성 코드, 허용 값 유형, 단위 규칙
  - node: 변경되지 않는 내부 식별자와 노드 유형만 공통 관리
  - node_name: 대표 이름·별칭·언어·적용 기간·변경 근거
  - external_identifier: 외부 체계와 식별값
  - node_merge: 기존 식별자와 기준 식별자, 병합 이유·처리자·시점
  - event_temporal_extent: 사건 시작·종료 시점과 시간 정밀도
  - 사람·회사·기술·주제의 세부 사실은 고정 프로필 열이나 JSON 속성이 아니라 Claim으로 저장한다.

  ### 근거 기반 지식그래프

  - knowledge_item: 노드·관계·Claim의 공통 현재 상태와 생성 계보
  - knowledge_state_event: 이전·새 상태, 이유, 처리 주체, 처리 시점
  - 승격된 지식 상태는 근거 확인됨 → 사람 확인됨/보류/거절로 관리하며 거절은 해당 기록에서 종료 상태로 취급한다.
  - relation: 시작 노드, 관계 유형 버전, 도착 노드, 관련 사건, 유효 기간
  - 같은 관계는 시작 노드 + 관계 유형 버전 + 도착 노드 + 관련 사건 + 유효 기간으로 판정한다.
  - claim: 원문 언어의 원자적 주장, 표현 성격, 주장 시간과 모델 계보
  - claim_relation: Claim이 관계를 지지하거나 반박하는 다대다 연결
  - claim_attribute_value: 대상 노드, 속성 정의, 값 유형, 문자열·숫자·날짜·참거짓·노드 참조용 열
  - DB 제약으로 Claim 속성값의 유형별 열 중 정확히 하나만 채우게 한다.
  - observation: 출처 버전, Unicode 문자 기준 [start, end) 위치, 인용문, 인용문 해시, 관측 시점
  - claim_observation: 하나의 원문 범위를 여러 Claim이 공유하고 하나의 Claim이 여러 관측을 갖는 다대다 연결
  - 정규화 본문은 UTF-8 NFC와 LF 줄바꿈을 사용하며, 인용문과 문자 위치가 일치하지 않으면 승격을 차단한다.

  ### 검증과 충돌

  - lint_run, lint_finding: 차단 검사와 경고 검사를 분리하고 대상·규칙·해결 상태를 기록
  - conflict_set: 비교 대상 관계·속성·기간과 Agent 제안, 사람 확인·거절 상태
  - conflict_member: 지지·반박 Claim 목록
  - conflict_summary: 공통 사실과 관점 정리, 모델·프롬프트 계보
  - 비교 가능한 근거 확인됨 Claim끼리의 충돌 후보만 지도에 호박색 점선으로 표시한다.
  - 충돌 후보 거절은 Claim 거절과 분리한다.

  ### 승격, 파생 데이터와 공개

  - promotion_batch: 후보 묶음, 승격 트랜잭션 상태, 생성된 기준 지식 식별자
  - 외부 수집·Agent 호출·lint는 트랜잭션 밖에서 수행하고, 검증된 묶음의 승격만 짧게 원자 처리한다.
  - node_embedding: 검색 문서와 모델·차원·벡터
  - node_context: 한국어 맥락 설명
  - followup_question: 노드마다 준비된 한국어 후속 질문 두 개
  - 파생 결과는 덮어쓰지 않고 버전별로 보존하며 같은 입력·버전 조합은 재사용한다.
  - publication_state는 promotion batch마다 준비 중·공개 준비됨·실패를 기록한다.
  - 영향을 받은 지식과 검색·임베딩·설명·질문이 모두 준비된 묶음만 다음 탐색부터 지도와 일반 검색에 포함한다.
  - 전체 지도 버전, 지도 구성원, 중심 노드별 부분 그래프와 3D 좌표는 저장하지 않는다.
  - 지도는 공개 준비된 지식에서 직접 이웃과 중요한 2단계 이웃을 조회하고 브라우저에서 좌표를 계산한다.
  - 열린 지도는 자동 재배치하지 않으며 다음 검색·노드 클릭·시간 범위 변경부터 새 데이터를 반영한다.
  - 거절된 지식은 공개 준비 상태와 관계없이 즉시 필터링한다.

  ## 3. 설계 순서와 의존성

  1. 용어, 불변 식별자, 언어, 시간 정밀도, 상태 집합과 문자 위치 표준을 정의한다.
  2. 온톨로지 버전과 노드·관계·속성 정의를 설계한다.
  3. GDELT 발견 기록, 출처, 불변 출처 버전과 독립 근거 묶음을 설계한다.
  4. 노드 정체성, 이름 이력, 외부 식별자와 병합 구조를 설계한다.
  5. 관계·Claim·속성값·관측의 카디널리티와 고유성 규칙을 설계한다.
  6. 후보 JSON, 후보 항목, lint, 상태 전이와 거절 fingerprint를 설계한다.
  7. 승격 묶음, Agent 재시도, 그래프 변경 계보와 공개 준비 상태를 설계한다.
  8. 검색 문서·임베딩·한국어 설명·후속 질문의 버전 구조를 설계한다.
  9. 동적 부분 그래프 조회에 필요한 논리 입력과 계산 가능한 시각 지표를 검증한다.
  10. HBF 예시 데이터를 모든 엔터티에 통과시켜 누락된 관계와 제약을 수정한다.

  ## 4. 검증과 산출물

  - logical-data-schema.md 한 파일에 논리 ERD, 데이터 사전, 키·카디널리티, 상태 전이, 불변조건, ingest·승격·공개 흐름과 HBF 예시를 작성한다.
  - 다음 시나리오를 논리 모델로 검증한다.
      - 같은 URL의 본문 변경이 새 출처 버전을 만들고 기존 Evidence Trace를 보존한다.
      - 잘못된 문자 범위와 허용되지 않은 관계는 승격되지 않는다.
      - 복제 기사 여러 건이 관계선 굵기를 한 번만 증가시킨다.
      - Agent 실패 시 원문만 남고 기준 그래프는 바뀌지 않는다.
      - 파생 결과 실패 시 기준 지식은 남지만 새 변경 묶음은 공개되지 않는다.
      - 재시도 성공 후 다음 탐색부터 새 관계와 설명이 함께 나타난다.
      - 관계 없는 노드도 검색·설명·질문이 준비되면 중심 노드로 표시된다.
      - 충돌 후보는 호박색 점선으로 나타나고 거절 시 Claim을 삭제하지 않고 점선만 해제한다.
      - 노드 병합과 사명 변경 후에도 과거 식별자·이름·근거를 추적할 수 있다.
      - 90일 지도와 1년 전체 기록 보기가 출처 게시 시점을 기준으로 다른 이웃을 반환한다.

  - 문서 검토가 끝날 때까지 PostgreSQL DDL, migration, API, 애플리케이션 코드와 새 dependency는 만들지 않는다.
  - 논리 모델 승인 뒤 별도 단계에서 PostgreSQL 타입·FK·CHECK·UNIQUE·인덱스, tsvector와 pgvector 차원을 물리 스키마로 변환한다.

  ## 5. 확정된 기본값

  - PostgreSQL을 목표 DB로 사용하지만 이번 단계는 DB 제품에 종속되지 않는 논리 모델이다.
  - 원문 HTML은 저장하지 않고 정규화된 텍스트만 저장한다.
  - Claim과 인용문은 출처 언어를 유지하고 한국어 표현은 파생 데이터로 관리한다.
  - POC 동안 출처·지식·상태 이력·계보·파생 결과를 자동 삭제하지 않는다.
  - 지도 배치와 부분 그래프는 재계산 가능하며 기준 데이터로 취급하지 않는다.
  - 기존 대화 원문 파일은 수정하지 않고 논리 스키마 문서만 새 작업 소유 파일로 관리한다.
